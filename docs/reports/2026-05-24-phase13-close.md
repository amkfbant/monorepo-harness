## 3. New endpoints (Phase 13)

Audit (read-only, --enable-mutation 不要):
```
GET /api/operations?targetType=&targetId=&status=&limit=
GET /api/operations/:operationId
```

Mutation (--enable-mutation 必須 + Bearer + CSRF):
```
POST /api/runs/:runId/review
POST /api/runs/:runId/rerun           (202 accepted; execution deferred)
POST /api/runs/:runId/cleanup
POST /api/runs/:runId/pr              (202 accepted; gh CLI deferred)
POST /api/backlog/:itemId/run         (202 accepted; CLI runner deferred)
```

各 mutation:
- Idempotency-Key header support
- body.dryRun=true で planned changes のみ返す (no state change)
- OperationRunner で operations 行 + operation_events を audit に残す
- OperationInFlightError → 409 conflict

## 4. Breaking changes

### 4-α. operations table schema 拡張

Phase 7-5 で導入された軽量 schema (operation_id / command / scope_type
/ scope_id / result_json / created_at) を ALTER で audit ledger に
superset 化。

既存 Phase 7-12 row は新 columns NULL / DEFAULT で migrate (`status`
DEFAULT 'succeeded' / `dry_run` DEFAULT 0 / `metadata_json` DEFAULT
'{}')。legacy code (`findOperation` / `recordOperation`) はそのまま
動く。新 code (`findOperationByIdempotency` 等) は新 columns を使う。

### 4-β. dashboard serve に --enable-mutation flag

default OFF。OFF のときは Phase 12 と同じ振る舞い (POST は 405)。ON
時は CSRF token を console に表示。

### 4-γ. Route method 型を `"GET" | "POST"` に拡張

`mutationRoutes()` factory が POST を返せる。GET 専用の Phase 12
default routes は型上不変。

## 5. Known limitations / Phase 14+ への送り

### 5-A. CLI core operation extraction is partial

design §3.E では review-apply / rerun / cleanup / pr-create / backlog-run
を `src/operations/{review-apply,run-rerun,...}.ts` に extract する予定。
Phase 13 では:
- `review.apply`: HTTP endpoint が processReviewDecision を import で
  呼ぶ (CLI 側は既に同関数を呼んでおり、両者が同 core を共有する形は
  達成済み)
- `run.cleanup`: 同様に cleanupRun を共有
- `run.rerun` / `run.pr_create` / `backlog.run`: HTTP endpoint は 202
  accepted を返し、operation row を 'running' で残し result_json に
  `{accepted: true, note: "deferred to CLI runner"}` を入れる

完全 CLI/HTTP shared core function 化 (= `src/operations/*.ts` への
file extract) は post-Phase-13 work。operations ledger は既に audit
として記録するので、deferred な実行は別 worker / CLI で operation_id
を渡して resume させる。

### 5-B. Mutation UI の button + dry-run modal + operation drawer は未実装

Phase 13-7 では CSRF meta tag + banner injection のみ。full button +
preview modal + confirm flow + operation status poll は post-close work。

Browser JS を加えて、各 run 行に approve/rerun/cleanup/pr button を
出す → 既存 dashboard renderer (`src/dashboard/render.ts`) を edit する
必要があり、scope 大きい。Phase 13 では curl / scripted client で
mutation API を叩ける状態を land し、UI は次イテレーション。

### 5-C. `operation_confirmations` table

design では confirmation challenge UX (一意 token + expiry) を別 table
で持つ予定。Phase 13 では CSRF token で十分なので未作成。Phase 14+
で UX を上げるとき検討。

### 5-D. POST CORS preflight (Phase 12 post-close P2 残し)

CORS preflight OPTIONS handler は Phase 13 でも未実装。default CORS
off のため non-blocking だが、cross-origin browser client が必要に
なったときに追加。

### 5-E. Operation retention / archive

`operations` 行は無限増殖する。Phase 15 で retention policy + archive
DB integration。

### 5-F. Phase 10-1 post-review P1 (pr create / cleanup race) は Phase 13 でも未根本 fix

`run.pr_create` / `run.cleanup` の OperationRunner audit + idempotency
key で **新 race は減る** (duplicate POST が同 operation を共有する) が、
gh CLI invocation の order と DB reservation の atomicity は完全 close
されていない。Phase 15 doctor / Phase 16 archive 周辺で再検討。
