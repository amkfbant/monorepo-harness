## 4. Breaking changes

### 4-α. `harness run show` / `run artifacts` / `run timeline` の default が files-first → DB-first

`--source <auto|db|files>` flag を追加し、default を `auto` (db-first run なら DB-first、legacy-file run なら files-first)。Phase 9 までは file 優先。

**移行:**
- DB-first run を file 経由で見たい時は `--source files` を明示。
- `harness db export-files --run <id>` で compat export を再生成して file を最新化することも可。

### 4-β. `harness lock release --source file|both` の deprecation

`harness lock` は DB lock only に。`--source file` / `--source both` は **deprecated warning** を出すが DB release を実行 (operator script 互換)。Phase 11 以降で `--source` flag 自体の削除を検討。

### 4-γ. `.harness/locks/*.lock` 残骸への warning

旧 file lock sentinel が残っていた場合、runtime command 起動時に 1 回 stderr warning。`HARNESS_SUPPRESS_LEGACY_FILE_LOCK_WARNING=1` で抑制可。

### 4-δ. runtime command の SourceModeError messege が "db-first" only に

Phase 9 までは "db-first | legacy-file"。Phase 10 で `db-first` only。`legacy-file` row が runtime command に来た場合は SourceModeError (= startup guard `assertNoLegacyRuntimeRows` で先に reject される、防御層)。

bypass: `db migrate-legacy` / `db import --force-legacy-reconcile` / `db doctor` / `db check-consistency` は legacy rows を扱う。

## 5. Known limitations / Phase 11 への送り

### 5-A. state_version の writer 統合は review-process 関連のみ

設計 §3.E.E5 は "全 writer state_version 統一" を要求するが、Phase 10-5 では:

- ✅ bump: `applyReviewDecision` / `forceFailFinalize` (lease-stolen finalize)
- ⏭️ 未 bump: `setStatus` / `setSafetyStatus` / `cleanupRun` / `createPullRequest` / `rerunFromReview`

review process の CAS は review-related transition のみ観測すれば足りるため、scope reduction は機能上問題なし。ただし design §3.E.E5 が言う "feature flag による段階的有効化はしない" 原則からは partial。Phase 11 で全 writer に bump 統合する。

### 5-B. runtime legacy-file branch の物理削除

Phase 10-6 では SourceModeError throw を `db-first` only に絞ったが、`if (dbFirst) { ... } else { /* legacy-file path */ }` の else branch が物理的に残置 (assertNoLegacyRuntimeRows で reach 不可)。Phase 11 で物理削除。

対象ファイル:
- `src/core/cleanup.ts` (cleanupUnderLock 内の legacy-file 分岐)
- `src/core/pr-creator.ts` (createUnderLock 内)
- `src/core/review-processor.ts` (processUnderLock 内 — file 経路の review-decision.yaml 読み)
- `src/core/rerun.ts` (file fallback)
- `src/core/backlog-db.ts` (backlog の legacy-file 経路)
- `src/core/knowledge-db.ts` (knowledge_candidates の legacy-file marker)
- `src/db/scopes.ts` (source_mode resolution helper)
- `src/core/run-viewer.ts` の `source_mode='legacy-file'` 分岐 (Phase 10-4 で auto は files-first、Phase 11 で削除可)

### 5-C. `harness db materialize` / `harness db materialize cleanup` CLI が未実装

設計 §5.2 が定義する CLI:
- `harness db materialize --run <id> [--ttl <duration>] [--out <dir>]`
- `harness db materialize cleanup [--expired] [--run <id>]`

Phase 10-3 で repository (`run-materializations.ts`) と record/cleanup hook を `ensureRunMaterialized` / `syncRunArtifactsToDb` に統合。CLI 露出は Phase 11 で minimum 実装 (主に `cleanup --expired` が `db doctor` worker として有用)。

### 5-D. post-run command の concurrent reservation

Phase 10-1 post-review P1 で指摘された:
- `pr create` 2 process 並行で external side effect (gh CLI) 前に DB reservation が無い → 2 process が同 PR を作る race
- `cleanup` の fs op が DB guard 前に走る → `pr create` と race

Phase 10-5 で state_version bump を review-process 関連のみに絞ったため、これらの transition は state_version を bump せず CAS で守られない。

Phase 11 で:
- `pull_requests.status='creating'` を gh CLI 前に INSERT (UNIQUE(run_id) で race 排除)
- `cleanup` を `runs.status='cleaning'` への CAS transition から開始 (state_version bump 統合)

### 5-E. Phase 10-5 codex review が最終応答未出力

codex (gpt-5.5, effort=medium) が Phase 10-5 review prompt に対して reasoning は走らせたが最終 message を生成せず exit。effort xhigh/high でも同様。Phase 10-7 phase 総合 review で Phase 10-5 を再 cover。

### 5-F. design §3.E.E2-bis operation_id transaction flow の完全 normative 実装は Phase 13

設計 §3.E.E2-bis は operation_id-based transaction flow を normative として要求するが、`operations` table 自体は Phase 13 で扱う schema v8。Phase 10-5 では `markProcessed` の `source_sha256` guard と既存 `operations` ledger を組み合わせて minimum 防御。

## 7. Phase 11 への接続

Phase 11 は "review governance / consensus" を導入する。Phase 10 で確立した:

- `review_proposals` の DB canonical 化 (Phase 9-8 + 10-5)
- `runs.state_version` (Phase 10-3 + 10-5 review-process 関連 transition で bump)
- `markProcessed` の source_sha256 guard (Phase 10-5)
- DB-only domain lock (Phase 10-1)

これらが Phase 11 の前提:
- `review_proposals.reviewer` (string) → `reviewer_id` (FK to `reviewers` table) への migration
- `runs.state_version` を consensus 再評価 trigger に流用
- consensus evaluator が markProcessed の guard と同じ pattern を使う

Phase 10-5 で送った "全 writer state_version bump" は Phase 11 で完成させる (consensus が cleanup / pr-create の transition も観測する必要があるため)。
